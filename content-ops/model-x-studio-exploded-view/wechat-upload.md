# 334个零件零重叠：这个开源项目把Model X拆给你看，核心算法只有33行

你在产品页上见过的3D爆炸图，十有八九是建模师手K的动画：哪个零件往哪飘、飘多远，全靠人眼对。零件一多，手工对位就是灾难，换个模型还得全部重来。

这周挖到一个上线刚6天的开源项目 **Model X Studio**，GitHub 218 star。它把一辆特斯拉Model X拆成 **334个零件**，而且每个零件爆炸后停在哪，全部由代码根据真实包围盒自动计算——不重叠、不出画，手机竖屏到桌面宽屏都算过。

我把线上demo实际点了一遍，又读完了全部核心源码（其实只有两个文件、不到300行）。结论先说：**做3D可视化的前端，这个仓库值得今天就克隆。**

![整车展示](/root/jackssybinIndex/content-ops/model-x-studio-exploded-view/media/01-assembled.jpg)

## 拖一下滑块，整辆车摊成一张零件矩阵

打开网页（纯静态，零后端），一辆银灰色Model X停在圆形展台上，车漆、玻璃、轮毂反光都到位。底部一条 Explode 滑块，0到100%。

拖到一半，车先按8大系统分层：玻璃上浮、电池下沉；越过40%之后，334个零件各自飞开，**最后在空间里平铺成一整面零件矩阵**，每个零件头顶挂着编号，滑块读数直接变成"334 pieces"。

![334件爆炸视图](/root/jackssybinIndex/content-ops/model-x-studio-exploded-view/media/02-exploded.jpg)

点任意零件，右侧弹出详情：原理介绍、规格表、单件选择器，还有个"隔离"按钮——一点，整个场景只剩这个零件，相机自动推近。

我实测时特别留意了加载过程：17MB模型下载期间中央有转圈提示，加载失败会给"重载视图"按钮而不是白屏；模型出来后拖滑块、自转、全屏、点选都跟手，手机宽度下UI会自动改成底部抽屉式布局，组件面板和详情面板不会同时挤在屏幕上。

## 33行代码，干了建模师三天的活

最值钱的文件是 `app/explosion-layout.ts`，33行。它解决的问题一句话：**怎么把三维零件在屏幕平面上摊开，保证任意两个零件投影互不重叠？**

拆成三步：

**第一，投影而不是三维打包。** 相机俯视方向固定，代码算出"屏幕右向量、上向量"，把每个零件包围盒的8个角点投上去，得到它在屏幕上的真实宽高。相邻的细碎饰条也能被分开，这是关键。

**第二，按行装箱。** 总宽度按全部零件投影面积开根号估算，然后从左往右摆，超宽换行——经典二维装箱，简单但够用。

**第三，反推三维位移。** 槽位中心映射回三维，每个零件的飞行向量 = 槽位中心减自身中心，全程只平移、不旋转。

而且这套布局是被脚本严格验证的：Node里真实加载17MB的模型文件，断言 **334个槽位、两两零重叠、三种屏幕宽高比下每个零件都在画面内**。相机距离也是按FOV反推出来的，留18%余量。

这意味着什么？**换个glb模型重跑一遍，整套爆炸视图自动成立。** 手K动画永远做不到这点。

## 几个能直接抄走的工程细节

194行的渲染主文件里，好东西密度很高：

- **双段爆炸**：系统分层和单件散开在40%–100%间用smoothstep渐变交接，不跳变；
- **场景会让路**：零件一散开，展台淡出、地面下沉、阴影关闭、雾从16米拉到400米——不然12米宽的零件矩阵一半泡在雾里；
- **标签用DOM按钮+三维投影**，每50ms才更新一次位置，而不是每帧重排几百个DOM；编号点用Points粒子渲染，点击靠屏幕距离手动命中；
- **转视角不误触**：21行状态机区分"点击"和"拖拽"，手指移动超过10px就不算点选；
- **性能克制**：阴影不自动更新、相机不动就跳帧不渲染、像素比封顶1.5，还完整支持"减少动态效果"系统设置。

## 334这个数字怎么来的：一条Blender自动管线

零件不是手工切的。仓库里的 `convert-model.py` 是一条离线Blender脚本，干的事很硬核：

源文件是创作者cgi Moon的Blender模型，脚本加载时**直接禁用脚本执行**（防供应链风险的意识）。Cycles渲染器专用的节点材质浏览器用不了，它就按材质名关键字全部重建为Three.js能吃的物理材质：车漆金属度0.55加清漆层、镀铬件金属度0.92、玻璃走透射、轮胎粗糙度0.72。

然后先把细分等修改器求值，再进编辑模式按"**不连通几何**"（LOOSE）自动拆分——这就是334个网格岛的来源。最后导出glTF和一份manifest，每个零件带编号、所属系统、中心坐标、尺寸和面数。

我翻了manifest，334件的真实分布是：车身180、车轮94、座舱38、玻璃12、车门10。脚本还在Node里实测了整车包围盒：**长5.056米、宽2.276米、高1.680米**，和真车数据一个量级。注意343是实际绘制网格数、334是可选零件数，作者连这两个数字都没混为一谈。

## 一个彩蛋：网页给AI助手开了个"工具"

页面代码里有一段 `document.modelContext.registerTool` 的特性检测：如果浏览器支持WebMCP协议（AI浏览器的网页工具标准），页面会主动注册一个 `explore_vehicle_component` 工具，参数限定为8个部件名、0–100的爆炸值、是否隔离，还带完整的输入校验。

想象一下以后的用法：直接对AI助手说"把电池隔离出来、爆炸到50%"，由网页自己暴露的工具驱动3D场景。作者同时老实标注：协议在真实浏览器里的执行效果**尚未验证**——能跑通的写功能，没验证的写未验证。

## 最让我有好感的，是这种克制

334件是艺术家切的"网格岛"，**不是特斯拉认证的售后零件号**；电池、电机、悬挂挂着橙色"示意件"徽标；年款未核实就写未核实。没吹"精准复刻"，也没假装是官方授权产品。

模型用BlendKit的Royalty Free许可、署名嵌入、不提供下载入口。想搬去商用，**17MB模型本身要先去读许可**，能放心抄的是那33行算法和整套工程方法。

## 怎么跑

需要Node.js 22.13+：

```bash
npm ci
npm run dev -- --port 3015
```

技术栈 React 19 + Three.js + Vite，Vercel导入即用，零环境变量。仓库同时保留了两条构建链：开发态走 vinext（Cloudflare 那套 RSC 构建），给 Vercel 的则是一条纯 SPA 出口，但两边共用同一套页面、样式和 Three.js 场景。

README还给了验证三连：TypeScript类型检查、在Node里真实加载模型跑爆炸布局断言、构建Vercel产物。我最认可的是中间这条——它验证的是"334个槽位零重叠、三种屏幕比例下不出画"这种**几何事实**，而不是截个图自我感觉良好。这也是我判断一个开源演示项目靠不靠谱的标准：有没有把验收条件写成机器能跑的断言。
