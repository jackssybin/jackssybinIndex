# 翻完 31 万行源码，我重新理解了"多智能体编程"：Aperant 到底是神器还是套壳

当 AI 编程助手普遍还停留在"一个对话框、一个任务、排队执行"的阶段，有一类工具开始探索更激进的命题：能否让多个 AI agent 同时在一个代码库里并行开发，并且保证它们互不干扰、能自我验证、还能自动合并。最近我通读了这类工具中关注度较高的开源项目 [Aperant](https://github.com/AndyMik90/Aperant) 的源码，它有 1.46 万 Star，前身叫 Auto Claude。

这篇文章不引用官方宣传语，只基于 1146 个 TypeScript 文件、约 31.4 万行代码的实际结构，回答三个问题：它的多智能体能力在工程上如何成立、"自主编码"的真实边界在哪、以及它当前所处的特殊阶段是否值得投入。

## 一、先厘清本质：它是 Claude Code 的编排层，不是新模型

源码层面最明确的一个事实是，Aperant 并不包含自研大模型。在 agent 进程管理模块中，它通过 Node 的 child_process 拉起 Claude Code CLI 子进程，再用环境变量隔离不同的配置目录和 OAuth 令牌。换句话说，真正写代码的智能仍然来自 Claude，Aperant 提供的是上层的工程化能力。

![Aperant 自主编码闭环：规划、并行构建、自验证、智能合并](media/pipeline.png)

因此它的三项硬性前置条件——Claude Pro 或 Max 订阅、本地安装 Claude Code CLI、项目必须是已初始化的 git 仓库——并不是营销话术，而是由架构决定的。把它理解成"Claude Code 的并行军团指挥官"比理解成"另一个 AI 模型"更准确。这也意味着它的能力上限和成本结构，都与 Anthropic 的服务深度绑定。

## 二、自主编码闭环：把需求拆成可调度的工程流水线

在编排目录下，可以看到一条完整的处理链路。规划阶段由规格编排器和子任务迭代器，把自然语言需求拆成结构化任务；并行阶段由并行执行器调度多个 agent；质量阶段由 qa-loop 构成验证回路；最后由合并模块处理冲突与集成。

有两个工程细节值得注意。其一是步数上限的设计，默认 maxSteps 为 200，简单任务被限制为 1，这从机制上避免了 agent 在异常情况下无限循环、持续消耗额度。其二是状态管理采用 XState 状态机，配合暂停处理和恢复管理器，让每个 agent 的生命周期可观测、可中断、可恢复，而不是失控的后台进程。

质量回路是它区别于聊天式工具的关键：测试失败会触发自动修正并重跑，同时用 QA_MAX_ITERATIONS 限制最大迭代次数，并能产出 QA 报告和人工测试计划。合并模块则强调语义级冲突分析，配合文件演变追踪和时间线记录，处理多个并行分支的集成。

## 三、并行安全的根基：git worktree 隔离

多个 agent 同时修改同一套代码，最大的风险是工作区互相污染。Aperant 的解法是 git worktree，而不是简单地复制目录。

![git worktree 隔离与 12 终端网格](media/worktree.png)

worktree 管理器为每个任务创建或复用独立的 git 工作树，每个工作树绑定独立分支，主分支保持只读。代码里可以看到完整的生命周期管理：用 git worktree add 创建、用 worktree list --porcelain 核验状态、任务结束后批量回收。这样任务之间的文件改动在操作系统层面就被隔离开了。

至于"12 个终端"这个常被引用的数字，它并非宣传口径，而是 UI 层终端网格组件里写死的 3 行 4 列布局常量，界面实时显示当前终端数与上限 12 的比值，预加载层也专门为这 12 路事件调大了监听器上限。

## 四、跨会话记忆：图数据库与五级嵌入降级

单会话的智能并不稀缺，真正的难点是让 agent 记住项目的长期上下文。Aperant 的记忆层用 libSQL（SQLite 的开源分支）实现了一套图数据库，核心是节点表、边表和闭包表。闭包表预先计算节点间的可达关系，并用深度上限 5 控制遍历成本；一个观察者模块监听代码变更以更新图谱，检索模块则在 agent 运行时按需把相关记忆注入上下文。

![基于 libSQL 图数据库与五级 embedding 降级的记忆层](media/memory.png)

嵌入服务的设计体现了本地优先取向，采用五级自动探测降级：本地 Ollama 专用模型优先，其次是 OpenAI 兼容接口、其他 Ollama 模型、主流开源嵌入模型，最终兜底为 hash 方案。需要客观指出的是，最后一级 hash 兜底不具备语义相似度，只能做字面匹配，所以完整的记忆检索体验仍依赖本地部署 Ollama 模型，这点官方文档和代码注释的口径是一致的。

## 五、安全机制与项目现状：评估时不可忽略的两条线

![Aperant 的真实定位与能力边界](media/limits.png)

让 AI 自主执行 shell 命令天然带有风险。它的安全模块给出了四层约束：操作系统级沙箱隔离 bash、文件系统操作限制在项目目录内、基于项目技术栈动态生成的命令白名单与黑名单、以及防止密钥外泄的扫描器。发布物附带 SHA256 校验和与 VirusTotal 扫描结果。但这些机制是降低风险而非消除风险，对自主产出的代码保留人工 review 仍然必要。

更影响选型决策的是项目的生命周期。当前 2.x 桌面版已进入维护模式，稳定版停留在 v2.7.6，最新 beta 的发布时间是 2026 年 3 月，此后没有新的正式发布。团队正在一个独立仓库从零重构 3.0，方向是在本地体验之上增加云端能力，协议保持 AGPL-3.0。官方明确解释仓库表面平静并非弃坑，而是主力开发迁移；同时由于代码要推倒重来，针对当前版本的代码 PR 已暂停，外部贡献目前只能通过 issue 和讨论区进行。

许可层面，AGPL-3.0 对个人使用、修改和内部部署比较友好，但若要基于它构建对外提供网络服务的闭源 SaaS，会触发相应的开源义务，需要商业授权。

## 结论

从源码看，Aperant 的真正贡献不是某个单点功能，而是把多智能体编程需要的并行隔离、质量回路、状态可控性和长期记忆，组织成了一套相对完整的工程系统。对于已经重度依赖 Claude Code、又被串行任务拖累的开发者，它展示的方向很有参考价值。

但两个约束必须同时纳入判断：第一，它是 Claude Code 的编排外壳而非独立模型，能力与成本都建立在 Anthropic 之上；第二，它正处于 2.x 维护、3.0 重构的过渡期，此刻更适合技术评估与小范围尝鲜，不宜在关键生产链路上做重投入。等 3.0 落地、PR 重新开放之后，再判断它能否承接长期工作流，会更稳妥。
