# 我把 50 万 Star 的 public-apis 克隆下来逐条解析：2465 个免费 API，到底能聚合出什么

做 Side Project 的人大概率都收藏过 [public-apis](https://github.com/public-apis/public-apis) 这个 GitHub 仓库——一个收集免费公共 API 的清单，Star 数已经达到 50 万，是全站 Star 量最高的项目之一。但"收藏"和"会用"之间隔着不少问题：这些接口真的能免费调吗、有多少需要注册 Key、浏览器能不能直接请求、以及最实际的——拿这么多 API 聚合起来，到底能做出什么产品。

我没有停留在读 README，而是把仓库完整克隆到本地，写脚本把那份 379KB 的 README 逐条解析，跑通了它自带的测试，再基于真实的分类条目数梳理聚合方向。这篇文章给出一手数据和我的判断。

## 一、它不是链接堆砌，而是一套有质量门禁的策展系统

先看实测的家底规模。

![仓库真实构成与工程化门禁](media/structure.png)

当前仓库收录 **2465 个符合规范的标准 API 条目，分布在 51 个分类**，另外今年新增了一个 **MCP Servers 专栏，收录 60 个面向 AI Agent 的 MCP 服务器**；累计约 2406 位贡献者、7019 次提交，MIT 协议，主语言 Python，2016 年建仓至今仍保持每日更新，没有归档。

它最反直觉的设计是：**整个"数据库"就是一份 README.md**，没有独立的数据文件，所有接口以 Markdown 表格维护，每行严格遵循六列契约——API（含文档链接）、描述、Auth、HTTPS、CORS、Link。其中 Auth 只接受 No、apiKey、OAuth 等固定枚举，CORS 只接受 Yes、No、Unknown 三个值。

这种做法能十年不失控，靠的是强制工程门禁。我读了 `scripts/validate/` 下的源码：format.py 校验字母序、字段数量和 CORS 枚举，links.py 在 PR 阶段自动巡检死链；`scripts/tests/` 下有 31 个单元测试，我用 CI 同款方式（`PYTHONPATH=. python3 -m unittest`）在本地跑了一遍，结果是 Ran 31 tests、全部 OK；外加 3 个 GitHub Actions 覆盖 push、PR 和链接检查。贡献指南还明确拒收营销性质的 PR，要求收录接口必须可免费公开调用。

换句话说，50 万 Star 的本质不是一份清单，而是"人工策展 + 自动化校验"长期治理的结果。它的分类也在跟着技术范式演进——这两年长出了 Cryptocurrency（114 个）、Machine Learning（61 个），今年又加了 MCP 专栏，我解析时还发现 24 个条目引入了给本地进程类接口用的 `stdio` 标记。

## 二、决定聚合可行性的，是认证和 CORS，不是接口总数

对要做应用的人，接口总数其实是最没用的指标，真正决定架构的是两个字段。

![认证与 CORS 分布，656 个接口可纯前端直连](media/auth-cors.png)

认证维度上，1200 个接口完全免认证（约 49%），1104 个需要 apiKey（约 45%），150 个走 OAuth（约 6%），剩余 11 个是 Mashape Key、User-Agent 之类的小众方式。接近一半的接口连注册都不需要。

跨域维度上，1080 个明确支持 CORS（44%），1055 个标注 Unknown（43%），330 个明确不支持（13%）。这里要澄清一个常见误读：Unknown 不等于不能用，只是清单没有验证过，需要自己发一次请求确认；而明确标 No 的，浏览器直连必然被拦，只能走后端代理。

两个条件取交集，得到一个关键数字：**656 个接口同时满足"免认证 + 支持 CORS"**。它的意义是，你不需要服务器、不需要申请 Key、不用处理密钥泄露，一个静态网页里的 `fetch()` 就能直连出数据。我从池子里抽样核实了几个真实接口：天气类的 Open-Meteo、NASA POWER，测试数据类的 DummyJSON、FakerAPI，娱乐类的 Cat Facts，金融类的 Billionaire Tracker，共性是注册零成本、文档清晰、返回标准 JSON。HTTPS 方面 2465 个里有 2377 个支持，安全基线整体不错。

## 三、核心问题：2465 个 API 能聚合出什么应用

这部分我没有拍脑袋，而是基于真实分类的条目厚度，挑出数据最密集、最适合聚合的赛道，逐个标注依赖分类、Key 要求、难度和变现路径。

![8 个可落地的聚合应用方向矩阵](media/ideas.png)

**① 个人数据仪表盘（难度★，订阅制）**：聚合天气（46）、加密货币（114）、金融（118），一屏看天气、持仓、汇率。大量免 Key 接口，是新手第一个项目的最优解。

**② 垂直行业情报台（难度★★，B 端 SaaS）**：用政务（142）、新闻（26）、开放数据（98）做政策、招标、监管监控。接口多需 apiKey，但 B 端愿意为替代人工盯盘付费，客单价高。

**③ 开发者 API 集市（难度★★，流量/佣金）**：基于最大的开发类（251）加测试数据（37），做可检索、在线试调、可收藏的 API 导航，本质是这份清单的产品化升级，靠 SEO 和置顶佣金变现。

**④ 旅行规划聚合器（难度★★，CPS 分销）**：交通（103）+ 地理编码（120）+ 天气（46）+ 汇率（35）组合，输入目的地给路线、天气、汇率、景点，接酒店机票分佣。

**⑤ 健身运动数据站（难度★，广告+会员）**：运动（76）+ 健康（54），做赛事比分、NBA 数据、球队排名，免 Key 接口密集、内容更新频率高。

**⑥ 娱乐内容盲盒（难度★，涨粉引流）**：游戏（120）+ 动漫（21）+ 音乐（39），做随机梗图、猫狗图、冷知识这类"一键来一条"，门槛最低，价值在涨粉而非直接变现。

**⑦ 加密金融看板（难度★★，交易导流）**：加密（114）+ 金融（118）+ 汇率（35），做实时币价、汇率、富豪榜，行情接口多免 Key，常见玩法是给交易所导流。

**⑧ MCP/Agent 工具网关（难度★★★，基础设施）**：用新增的 60 个 MCP 服务器加开发类 API，做面向 AI Agent 的统一鉴权、用量统计、请求路由。技术难度最高，但卡位 Agent 时代基础设施，想象空间最大。

需要说明，不同方向会复用同一批接口（天气、金融被多个方向共用），所以各方向数字相加会超过 2465，这是正常的，2465 是去重后的总数。选择上我的建议是：练手选①⑤⑥这类免 Key 密集、一个周末能出活的；想赚钱优先看②和⑧，壁垒和客单价最高，但需要后端能力；最忌讳一上来做"大而全的 API 导航"和原清单正面竞争，垂直切细分人群更容易跑出来。

而无论哪个方向，图底部那条共同前提都成立：**先做好健康度巡检、统一缓存、鉴权代理这三层底座**，否则免费接口的限流和失效率会很快拖垮体验。

## 四、边界：它是黄页，不是免运维的数据中台

高 Star 容易制造"靠它就能躺着做产品"的错觉，但边界必须在动手前接受。

![能力边界与生产环境建议](media/verdict.png)

它是人工策展的免费 API 黄页，字段规范、可按 Auth/CORS 筛选、跟进了 MCP 生态、MIT 协议允许自由复用元数据；但它不是数据服务平台——不保证接口长期可用（当前有 2811 个未关闭的 open issue，其中不少就是失效反馈），不提供托管、SLA、统一鉴权或缓存，免费额度和限流规则全由各服务商自定，而且 43% 的接口 CORS 状态是 Unknown，前端直连必须实测。

所以生产环境至少做到三点：后端加代理层、密钥永远不进前端；定时健康检查加自动降级的备用源；核心业务不要只依赖单一免费接口，同时严格遵守各 API 的服务条款。

## 结论

public-apis 最大的价值，是把"找数据"这件极耗时的脏活，变成了一个可检索、可筛选、有质量门禁的起点。它本身不构成壁垒，**真正的壁垒是你在它之上做的聚合逻辑、缓存策略、产品体验和接口选型**。

如果你是想练手的独立开发者，建议从 656 个"免 Key + CORS"接口池里挑一个方向，先在浏览器 Network 面板手动发一次 fetch 确认能返回 JSON，再写代码、加超时和缓存，从能跑的 Demo 平滑演进到能用的产品。
