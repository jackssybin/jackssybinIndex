# 翻完 58 万行源码，我重新评估了"AI 自动做短剧"这件事：影策到底是不是玩具

过去一年 AI 视频工具爆发，但创作者的真实工作流依然是割裂的：剧本在一个软件、角色图在另一个、视频生成在第三个、剪辑又换到第四个，素材靠文件夹和网盘来回搬运，角色形象还经常在不同镜头里"变脸"。单点生成能力越来越强，完整生产链路却始终没有被很好地打通。

最近有读者让我看看 [影策 open-ai-canvas](https://github.com/ddcat-ai/open-ai-canvas)，一个 MIT 协议的开源 AI 影视与短剧工作台，1747 Star，主打从小说到成片的完整流水线。我没有只看 README，而是把整个仓库克隆下来通读了源码。这篇文章基于实际代码，回答三个问题：它的生产链路怎么运转、上百个模型如何被统一管理、以及它距离真正可用还差什么。

## 一、先建立正确预期：这是一个全栈平台，不是轻量脚本

代码规模是理解这个项目的第一把钥匙。后端用 Go 1.25 编写，基于 Gin 和 GORM，共 1436 个 Go 文件、约 30 万行，internal 目录下有四十多个业务模块，覆盖 agent、画布、生成任务、支付、模型供应商、技能、工作台等。前端用 Bun、React 19 和 Vite，共 1389 个 TypeScript 文件、约 28 万行，状态管理用 Zustand，本地降级缓存用 localForage。

![影策的五层全栈技术架构](media/architecture.png)

除此之外，仓库里还有 112 个模型协议插件、六套不同用途的 docker-compose 编排、Nginx 配置、完整的管理后台和支付插件。合计约 58 万行代码的体量，决定了它的定位是"可以自托管的影视生产平台骨架"，而不是下载即用的小工具。如果你期待的是双击安装、零配置出片，这个预期需要先调整。

## 二、小说到成片：一条强调人工接管的生产流水线

影策的核心产品形态是短剧制作流水线，可以拆成四个阶段。

![从小说到成片的短剧制作流水线](media/pipeline.png)

第一阶段是输入与拆解，上传小说或粘贴正文后，系统按集拆分剧本，并提取角色、道具、场景。第二阶段是结构化分镜，每个镜头被标注景别、运镜和时长，并且与小说原文逐条对照；角色会生成三视图、别名、外貌和声线，一旦锁定形象，整部剧沿用同一套设定，这是针对 AI 视频常见的人设漂移问题做的设计。第三阶段是逐段视频生成，从第二段开始，系统自动把上一段的最后一帧作为下一段的首帧，用首尾帧衔接维持镜头连贯。第四阶段进入时间线，完成片段编排、修剪、字幕转写和服务端合成导出。

值得注意的是它的产品哲学并非"黑盒一键出片"。流水线的每个环节都开放人工接管：可以改写台词、锁定角色、对单个镜头重新生成。AI 承担执行，人保留对关键质量节点的控制权，这种协作式定位比承诺全自动要务实。

## 三、112 个模型插件：用一份合同收编厂商差异

工程上最值得讲的，是它的模型接入方式。影策没有把任何一家供应商写死，而是把文本、图片、视频、音频能力全部插件化。我对 plugin-packages 目录做了清点：文本类 23 个、图片类 17 个、视频类 22 个，其余 50 个涵盖音频、语音合成、ComfyUI 与 RunningHub 工作流以及支付应用，合计 112 个。

![112 个模型协议插件与 Manifest 合同机制](media/plugins.png)

我打开一个真实视频插件的 manifest 配置，它的合同结构相当严谨。首先是身份与版本，通过 apiVersion 控制宿主兼容性；其次是权限声明，插件能用哪些能力必须显式列出；核心是统一字段映射，用一套声明式表达式，把影策内部的标准参数（提示词、参考图、画幅、时长等）翻译成具体厂商要求的请求结构，同时用 validations 把厂商约束（例如参考图数量上限、不支持纯音频）前置到宿主侧拦截；最后是响应归一，把不同厂商风格迥异的返回字段统一收敛成标准的任务编号、状态、视频地址和用量，临时媒体地址则标记为临时资源，由宿主立即下载持久化，错误语义不被包装成成功。

安全边界也比较克制。根据插件系统设计文档，插件不能直接访问 React 组件、Cookie、API Key 或数据库，也不能自行注册后端路由和数据模型，远程网页插件必须运行在沙箱里并通过宿主 RPC 通信；错误、超时、权限拒绝和版本不兼容都要求显式暴露，不允许静默降级。第三方包统一使用专属后缀并按系统、官方、自定义三级管理。

## 四、无限画布、3D 引擎与 Agent：差异化能力的真相

除了线性流水线，影策还提供一块无限画布，用节点组织图片、视频、文本、音频和 3D 预演，支持节点连线、框选、小地图、撤销重做和只读分享。画布上的 Agent 可以结合素材、技能和画布上下文直接生成或修改节点，但它的生成操作仍然要经过审批和额度检查，而不是无约束地改动作品。

更前沿的是仍在内测的 3D 世界引擎，前端依赖显示它基于 React Three Fiber 和 three.js 实现。创作者可以在三维场景里布置布景、安排摄影机位，在地面标记 A、B 点后用自然语言指挥角色移动并生成关键帧，再导出白模视频和深度图，作为下游视频生成模型的参考。这个方向如果成熟，能显著提升镜头的可控性，但需要强调它目前仍是内测能力，不应按正式功能预期。

## 五、祛魅：MIT 友好，但门槛和边界同样真实

![上手门槛与安全边界](media/limits.png)

先说成本。软件本身 MIT 开源、可以免费使用和二次开发，但所有图片、视频生成调用的模型 API 费用完全由使用者自己承担，影策只负责渠道管理，并不替你付费，量产视频的账单需要自己评估。

再说部署。本地运行需要 Bun、Go 1.25 和 Docker Compose，对没有运维基础的个人创作者有一定门槛；项目还在高速迭代，官方也明确提示数据结构和外部接口可能调整。

安全是最需要认真对待的部分。README 明确建议默认在个人、本地或可信环境部署，未经安全配置不要直接作为公网多人服务。具体要求包括：公网环境关闭开放注册、CORS 不能使用通配符、后端默认拦截指向私网和链路本地地址的模型请求以防 SSRF、API Key 不得出现在 URL 或日志中、后端端口保留在容器网络内不直接暴露。官网提供的公开演示账号只适合体验，不适合存放敏感内容。

## 结论

从源码看，影策的核心价值在于把原本散落的 AI 影视生产环节，收敛成一个数据互通、允许人工接管、并且可以完全私有化部署的工作台；而基于 Manifest 的插件合同体系，让它具备了不被单一模型供应商绑定的工程弹性。这两点在同类开源项目里确实少见。

但它不是零门槛的魔法。58 万行的全栈体量、对 Docker 和 Go 环境的要求、模型费用自理，以及仍在演化的接口和内测中的 3D 能力，都决定了它更适合有一定技术能力的创作者、工作室或小团队，作为可掌控的生产底座来评估，而不是指望开箱即得地批量产出成片。建议先用官方在线演示完整走一遍流程，再决定是否投入精力本地部署。
