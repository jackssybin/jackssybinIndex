# 翻完 NovelToGame 的 7 个 skill 和两款实机游戏，我明白了 AI 做游戏差的到底是什么

这两年"AI 生成游戏"的概念很热，但真正用过这类工具的人往往会失望：它们大多能产出漂亮的概念图、成段的世界观设定，却交不出一个能稳定运行、可以通关的东西。问题往往不在模型不会写代码，而在缺少一套约束——没有清晰的阶段分工、没有对原著的尊重、没有可复现的验收标准，过程全靠随机发挥。

最近我认真读了一个刚过千 Star 的开源项目 [NovelToGame](https://github.com/zenstory-ai/novel-to-game)，它的切入点恰好是补上"规矩"这一层。它不是又一个游戏生成 SaaS，而是一组可以装进 Claude Code、Codex、Kimi Code 的 Agent skill，把资深策划的改编方法论固化成工作流。这篇文章基于它的七个 skill 文档、流程契约和两个完整可玩示例，谈谈它的设计思路和真实边界。

## 一、先厘清形态：skill 是方法论，不是可执行软件

这个仓库的主要语言是 Markdown，这本身就说明了它的产品形态。它交付的是七个结构化技能，而不是一个带界面的应用。使用者需要先具备编码 Agent 环境，通过一条命令安装，例如在 Claude Code 中执行 `npx skills add zenstory-ai/novel-to-game -g -y -a claude-code -s '*'`。

![7 个 skill 串成的改编流水线](media/pipeline.png)

真正执行编码、运行测试的是底层的编码 Agent，skill 扮演的是"改编总监"的角色：它规定每个阶段做什么、产出什么文档、用什么标准否决方案、在哪些节点必须等待人工决策。七个技能中，novel-to-game 是负责编排的总入口，其余六个分别承担拆书、概念选型、世界设计、美术方向、构建和验收。它还提供 director 模式，在概念方向、白盒裁剪、视觉目标三个节点停下来等用户拍板，以及 resume 模式读取进度文件从断点续跑。理解"模型负责执行、skill 负责流程与门禁"这个分工，是评估它价值的前提。

## 二、忠于原著：把事实分级，把发明标注出来

AI 改编最常见的硬伤，是把模型自己补全的内容当成原著既有设定。NovelToGame 在拆书阶段用一份 SOURCE_BIBLE 来约束这件事。

![原著事实四分类与工作区文档契约](media/contract.png)

它要求通读全书后，把关键事实归入四个类别并标注章回或文件出处：immutable 是不可改动的世界硬规则和关键转折；adaptable 是可以为玩法让路的弹性设定；open 是原著留白、允许原创的部分；conflicted 则是原著自身前后矛盾、需要显式标出而不是强行圆回来的地方。凡是原著没有、由改编新增的内容，一律标注为"设计发明"，不允许冒充原著。

这套机制的价值在于可追溯。后续所有设计决策都能回溯到事实库里的依据，而不是建立在模型的模糊记忆上。对于有版权约束、需要对原著负责的改编项目，这种考据纪律比单纯追求生成速度重要得多。

## 三、概念选型：用硬性否决对抗换皮模板

确定玩法方向的概念阶段，它没有让模型直接指定一个品类，而是要求横向比较多个可行方案，再用明确的否决标准筛选。文档里给出的淘汰条件很能体现策划判断：核心循环脱离原著核心冲突、去掉专有名词后只剩通用换皮模板、玩家仅仅是消耗资源解锁既定剧情，命中任何一条都会被否决。

同时它强调职责隔离。概念文档、游戏设计文档、美术方向文档分别由对应技能负责，一旦定稿，构建阶段不允许擅自推翻。这针对的是 AI 生成的典型顽疾——边做边改、目标漂移，最后产出一个什么都沾一点、什么都不深入的四不像。借鉴成熟品类时，还要求保留该品类的基础体验外壳，比如做回合制 RPG 就不能只交一串战斗关卡，进入世界、目标指引、成长反馈这些玩家预期都要明确实现或说明为何简化。

## 四、白盒先行与六项实机门禁

构建阶段的做法相当工程化。在批量生产美术资产之前，先用白盒原型验证头号设计风险，也就是那个"如果不成立，整个游戏就不成立"的核心玩法。白盒试玩要求另起一个没有读过设计文档和源码的独立 Agent 会话，仅凭画面和常规输入来玩，尽量模拟真实玩家视角，并如实记录输入、预期与实际差异。

真正让它区别于普通提示词合集的是验收环节。game-qa 要求游戏在目标环境真实启动，通过一次完整运行验证六项指标：启动、渲染、输入、核心循环、至少一个设计结局、重新开始。自动化状态只有 NOT_RUN、FAIL、PASS 三种取值，没有真实运行记录就永远停在 NOT_RUN，不允许口头声称完成。未覆盖的环境和特性则写进 limitations，而不是含糊带过。

## 五、两个示例证明它产出的是真游戏

方法论如果没有落地样本就只是空话。仓库提供了两个完整示例，都可以在浏览器在线试玩，并且附带从原著拆解到实机验收的全套工作区。

![两个真实可玩示例的代码规模与验收记录](media/examples.png)

《西游记·三借芭蕉扇》是一款梦幻西游式回合制 RPG，改编自原著第五十九至六十一回，包含 191 个文件、约 1.09 万行 JavaScript，实现了场景行走、自动寻路、五行相克和指令回合制战斗。它的验收记录里六项检查全部为 PASS，同时 limitations 诚实说明该次完整运行只覆盖了桌面分辨率下的本地 Chromium，移动端和其他浏览器并未实测。

《金瓶梅·风月总账》（标注 18+）则是古风恋爱互动影游，含五条人物线、十六个结局，关键选择会触发专属剧情过场而非动图充数，并提供快存、剧情树和 CG 鉴赏。这个例子展示了它对互动叙事的另一条要求：人物关系通过神态、称呼、可进入的场所来体现，而不是简单挂一个好感度数值。

## 六、理性看待边界：它放大能力，也暴露模型上限

![NovelToGame 的适用人群与能力边界](media/limits.png)

几个前提必须讲清楚。首先，它是技能而非开箱即用的应用，使用者要先有 Claude Code、Codex 或 Kimi Code 的使用习惯与对应订阅，所有生成消耗的是自己的 Agent 额度，复杂项目的时间和 token 成本并不低。其次，skill 能保证流程严谨、环节不缺失，但成品质量的天花板仍然由底层模型决定，它无法让一个能力有限的模型凭空做出优秀设计。

再者，它的目标场景是浏览器小游戏、文字冒险、互动影游这类可玩原型，大型 3A 项目或重度商业引擎并非其适用范围，生成的代码依然需要人工 review 和测试。版权友好的一面是：配音默认关闭、运行期实时合成需要在产品简报中显式批准，原著全文和设计文档不会外传。许可证采用宽松的 MIT，商用与二次开发基本没有障碍。

## 结论

NovelToGame 真正值得关注的，不是"AI 能做游戏"这个已经不新鲜的命题，而是它把资深游戏策划脑中那些隐性的质量标准——原著考据、方案否决、白盒验证、实机门禁、职责退回——转化成了 AI 可以严格执行的显性流程。它承认模型的不可靠，于是用文档契约和状态门禁把不确定性关进笼子。

对于有故事、想做游戏化尝试，但缺乏完整开发团队的创作者，它提供了一条有章法、可追溯、且终点确实是"能玩"的路径。但合理的预期是把它当作一位方法论扎实的 AI 改编总监，而不是一台承诺一键出大作的机器。
