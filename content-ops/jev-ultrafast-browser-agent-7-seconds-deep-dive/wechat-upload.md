你让 AI 帮你在网页上订个票，它通常是这样干活的：先看一张截图（上千 token），想想要点哪，再看一张截图，再想想。表单稍微复杂点，几十轮对话、几十秒时间就过去了；页面上一个动画弹出来，它刚想好的动作还可能当场作废。

这周，做出 6 万 Star 浏览器自动化框架 browser-use 的团队，开源了一个思路完全反过来的新项目：**Jev Ultrafast**（仓库链接已放在文末「阅读原文」）。官方实测成绩是——在真实的 Google Flights 上，一句自然语言指令，搜出「苏黎世→伦敦、单程、经济舱」的航班，**全程 7.073 秒**，录屏 1 倍速无剪辑，路线和日期还有独立程序复核。

![Jev Ultrafast 实测结果：谷歌机票已显示苏黎世飞伦敦 9 月 20 日的单程航班，右侧面板定格在 7.07 秒](/root/jackssybinIndex/static/images/jev-ultrafast-browser-agent-7-seconds-deep-dive/flights-result.png)

## 不让模型写代码，只让它做选择题

它的做法可以一句话概括：**模型在整个任务里只做「选择题」，永远不生成选择器、坐标或 JavaScript**。

每打开一个页面，注入页面的脚本会对 DOM 做一次原子快照，把可见控件编号成一张表：

```text
[1] button    票种 · 往返
[2] combobox  出发地 · 旧金山
[3] combobox  目的地 · 空
```

动作只有八种：点击、输入、下拉、上下滚动、等待、完成、卡住。然后一次请求同时问模型两件事：该做什么操作？如果是点击，点哪个？如果是输入，填哪个框？**两个决策，一次网络往返**，中位决策延迟只有 178 毫秒。

真正执行时，程序拿的是快照阶段保存好的真实 DOM 节点，模型给的只是一个编号。这等于从根上断掉了「模型吐出一段恶意脚本被直接执行」的可能。

这套设计还有一个反直觉的好处：因为每轮只传结构化文本而不是图片，一次决策的输入压到很小；官方录制里全程 17 次决策请求，输入 token 合计 90,558、输出 6,325，平均到每一步判断上的成本几乎可以忽略。换句话说，传统方案里「看截图」的钱，在这里整个被省掉了。

## 自由文本怎么办？只在需要时叫便宜模型

城市名总不能靠枚举。Jev 的分工很抠门：只有选中「输入」操作时，才去调一个小模型写字，而且返回必须是一个只含文本字段的小 JSON，多一个字段都不认，解析失败就一个字不填。

实测中生成 "Zurich" 花了 581 毫秒，"London" 花了 346 毫秒，两次调用合计费用 **0.00006272 美元**。贵模型做判断，便宜模型只出场两次写字。

## 快 25% 的底气：一份很克制的实测

![新旧循环对比：中位耗时 9.45 秒降到 7.09 秒，浏览器协议调用从 1092 次砍到 101 次](/root/jackssybinIndex/static/images/jev-ultrafast-browser-agent-7-seconds-deep-dive/perf-table.png)

官方没有只拿一个最快录屏说事。同一任务、同一浏览器、同一模型版本，新旧代码交替跑了 3 对共 6 次，全部通过独立校验：中位耗时 9.45 秒降到 7.09 秒（-25%），决策请求 22 次降到 17 次，**浏览器协议调用从 1092 次砍到 101 次**。

协议调用为什么能少一个数量级？旧循环反复读取可访问性树，而且页面上任何 DOM 变动——哪怕只是个动画——都会让决策作废重来；新方案一次调用拿齐控件，只比较语义状态，动画不再触发重算。报告同时老实承认：样本只有 3 对，统计检验不显著，这不是通用跑分。

这里藏着一个容易被忽视的工程取舍。「动画不触发重算」不代表完全不检查——恰恰相反，程序把检查分成了两层：普通的页面变化（远处一个轮播图在转、一条广告在刷新）被允许忽略，但在真正点击或输入的前一瞬间，会重新核对五样东西：目标元素还在不在、是否可见、是否可点、最新几何位置、以及点击点是否被别的浮层挡住。任何一样不通过，这次动作就放弃重算。这个「平时宽松、动手前严格」的分层，是它既快又不容易点空的关键。

等待时机的设计同样讲究。普通操作后最多等两个动画帧（约 50 毫秒）就立刻进入下一轮判断；但在搜索框这类带自动补全的组合框里输入后，会专门等下拉建议出现、上限 200 毫秒——因为如果建议还没出来就让模型选，它只能对着一个不完整的弹窗瞎猜。录制中点击搜索按钮发生在 5.217 秒，最后确认任务完成在 7.073 秒，中间谷歌结果页的加载等待一分不少地算在账上，没有快进。

## 自己跑，只要五行命令

```bash
git clone https://github.com/browser-use/jev-ultrafast.git
cd jev-ultrafast && uv sync
cp .env.example .env   # 填两个 API Key
uv run jev
```

注意需要两个 Key：TypeSafe 的决策模型 Key，以及写字用的 OpenAI 兼容小模型 Key（示例用 OpenRouter 上的 Mercury 2.5，也可以换成 DeepSeek、Gemini、GLM）。Chrome 连接出问题时跑一句 `uv run browser-harness --doctor` 自检即可。

打开本地网页点「Run automatically」即可。配套的检查器会把页面上每个控件编号，实时显示操作概率和置信度，你也可以选择每步手动确认——比如官方实测的第一步，模型以 76% 概率判断该「点击」，并以 93% 的压倒性概率选中票种下拉框，先把默认的往返改成单程，执行顺序和有经验的人类操作完全一致。核心代码只有六个文件，一个下午能读完。

## 谁该现在用，谁该再等等

我的判断很明确。标准表单类网站（订票、酒店、后台系统）的流程自动化、研究「结构化状态 + 一次往返」新架构的工程师、对 token 成本敏感的团队，现在就值得试。

但要注意它的边界：**Shadow DOM、iframe、canvas、文件上传、弹窗新标签、复杂键盘组件目前都不支持**，遇到会直接报卡住；标签页共享你本机已登录的 Chrome 配置文件，便利和风险是一体两面；项目还在 0.1.0 阶段，重要任务务必自己写结果校验，别信它自己说「完成」。

浏览器 Agent 的竞争，正在从「谁的模型更聪明」转向「谁让模型干的事更少、更确定」。这个项目给出的答案，至少在那 7 秒真实机票页上，是成立的。
