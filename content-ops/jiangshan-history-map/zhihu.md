# 读了「江山时序」的源码：一个零框架项目，如何用原生 JS 承载两千四百年中国史

读史书时一个很具体的困惑是地理的迷失：苏东坡笔下的黄州、韩愈"雪拥蓝关马不前"的蓝关、岳飞北伐的朱仙镇，在今天的地图上对应哪里？长安在两千年里换过多少个名字？疆域又是怎么从战国七雄一步步演变成今天的形状？最近一个 7096 Star 的开源项目 [江山时序](https://github.com/DeanChensj/jiangshan-map) 试图用一张可交互的历史舆图回答这些问题。

比起题材，它的工程实现更让我意外：这是一个数据相当密集的历史 GIS 应用，却没有使用任何地图或可视化框架。我把仓库克隆下来逐文件读了一遍，这篇文章谈三个问题：它如何用纯原生 JavaScript 撑起两千四百年的时空数据、四种交互背后的设计，以及作为个人数字人文项目，它的可信边界在哪里。

## 一、零依赖的技术选型：没有 package.json 的前端项目

首先注意到的是，项目根目录没有 package.json，也没有 node_modules。它由 17 个原生 JavaScript 模块构成，合计约 3.45 万行，最大的 app.js 超过一万行。我在 index.html 和启动脚本中确认，没有引用 leaflet、mapbox、openlayers 或 d3，地图投影、SVG 路径生成、交互命中检测全部自研，第三方资源仅有网页字体、访问统计和监控脚本。这意味着双击 index.html 就能离线运行整个应用，部署则是一个三行的 nginx-alpine Dockerfile。

![江山时序的四层架构与零依赖技术选型](media/architecture.png)

数据层按 18 个历史时期组织目录，从战国、秦、西汉一路到民国和当代，共 206 个 GeoJSON 文件、约 32MB，另有 205 个时序快照。项目还提供简体、繁体、英文、日文四种语言的文档和界面字典。在当下前端工程普遍依赖重型工具链的氛围里，这种"返璞归真"的选择本身就值得研究。

## 二、四种交互：让地图成为阅读历史的接口

README 把功能归纳为四种玩法，我在源码中逐一对应到了具体模块。

![江山时序的四种交互玩法](media/gameplay.png)

第一种是拉动时间轴看天下分合，也是整个应用的主轴。拖动滑块时，并立的多个政权以高对比度的宣纸设色同屏呈现，战国七雄、三国群雄、宋辽西夏大理金的对峙可以一屏看全。切换到重大事件节点时，新的疆域浮现，上一阶段以朱砂虚线残影保留在画面上，盈亏对比非常直观。时间轴上方的气泡同步显示当年在位君主与年号，黄河改道、云梦泽与罗布泊的消长、历代长城运河、古海岸线进退都会随年代变化。

第二种是点地溯源。点击古城或名关，会展开一张卡片：顶部是城市题记小传，下方是从战国的郡、汉代刺史部、唐代的道、宋代的路，直到元明清行省和现代省市的完整沿革表，本地发生的大事按朝代内嵌。函谷关、潼关、剑门关、玉门关等雄关用专门的汉阙城楼图标标注，还能把现代省界叠加到古图上做古今对照。

第三种是点人溯事。搜索人物后，地图以编号图钉标出其一生行迹，随着站点切换，年份、版图、年号跟着人物脚步流转。目前内置秦始皇、张骞、诸葛亮、玄奘、李白、苏轼、王阳明七人的完整行迹，并支持多人物同看——比如同时输入李白、杜甫、高适，轨迹合并到一条时间轴，同年同地的相逢标记为"同途"。楚汉之争、安史之乱、靖康之变三个历史事件则各以十个节点分三幕展开。

第四种是舆图寻址测验：隐去全部城名，只给出当朝掌故线索而不剧透现代地名，让用户凭山水直觉落针，按同心圆环的距离打分，十题结束授予太史令、职方郎中这类传统官阶。另有基于浏览器语音合成的自动讲解。

## 三、数据模型：疆域快照里装了什么

这个项目最见功力的是数据组织。我阅读了 atlas_snapshots.js 中的快照结构。

![疆域快照的数据模型与压缩工程巧思](media/data-model.png)

每个快照包含几类字段：caption 是年代区间与标题，note 是一段完整的史事考辨文字，prefRef 和 regionRef 指向政区与疆域 GeoJSON，polities 数组以数字 ID 列出当时并立的全部政权，regions 与 prefectures 则索引疆域面和州郡。以 648—656 年的快照为例，它详细记述了阿史那社尔平龟兹、设置安西四镇与王玄策破中天竺的始末。这意味着它呈现的不是孤立色块，而是"政权—疆域—政区—史事"互相关联的结构化知识。

为了让 32MB 数据适配纯静态站点，作者做了几层压缩，我在解码函数里确认了实现：地理坐标采用每字符 5 位的自定义编码，ring() 函数把字符串解码为经纬度增量数组，用相对位移替代绝对坐标；相同几何形状通过 shape 特征缓存复用；政权和政区统一用数字 ID 索引，快照之间只存引用不复制数据；GeoJSON 按朝代拆分实现懒加载；网页字体也做了子集化，只加载实际使用的字符。这些都是专业地理信息系统才会认真处理的细节。

此外，works.json 收录 26 部典籍，topics 目录有 34 个静态专题页，根目录的 llms.txt 方便内容被检索和 AI 引用。数据与表现分离，让同一套史料可以同时驱动地图、人物行迹、测验和多语言界面。

## 四、Deep Links：让每个历史瞬间都可引用

一个容易被忽略但很实用的设计是深度链接。应用的每个状态都映射到 URL 参数：year 指定年份，place 定位地点，person 展开人物路线，多个年份和地点还能组合出一条历史路径，比如用 1079、1080、1094、1097 四个年份配湖州、黄州、惠州、儋州，就能复现苏轼"黄州惠州儋州"的贬谪路线。加上 embed 参数即可进入 iframe 嵌入模式。

这让它天然适合教学和内容创作：老师讲安史之乱、作者写诗词赏析时，可以把精确到年份和地点的历史画面作为链接分享，或直接嵌进博客、Notion 和课程页面，配合 PWA manifest 还能安装为离线应用。

## 五、可信边界：数字人文不是权威地图集

![江山时序的价值与能力边界](media/limits.png)

欣赏之余，几条边界必须讲清楚。

其一，它是个人项目而非权威历史地图集。作者在贡献指南中明确把它定位为数字人文作品。古代政权的实际控制线本来就难以精确还原，图上的疆域边界是示意性的，不能当作精确国界引用；严肃的历史地理研究仍需回溯谭其骧主编《中国历史地图集》等原始文献。

其二，快照的时间密度并不均匀。战国、唐、清等资料丰富或变动剧烈的时期切片很细，少数时期相对粗疏，这是史料分布决定的客观限制。

其三，协议是 GPL-3.0 而非宽松的 MIT，这对二次开发影响很大：GPL 具有强 copyleft 传染性，把它的代码或数据整合进自己的项目并分发，衍生作品通常需要以同等协议开源；个人学习、内部使用或仅做 iframe 嵌入则不受影响。

其四，它没有后端数据库，史料修正全部依赖 GitHub 上的 Pull Request，语音讲解也依赖浏览器自身的 TTS 能力，跨设备的音色和支持度存在差异。

## 结论

江山时序最打动人的地方，在于它用一种近乎古典的方式做现代数据可视化：不追框架、不堆依赖，靠 17 个原生模块和严谨的数据建模，把两千四百年的政权更迭、政区沿革和人物行迹组织成一个可探索、可引用、可离线运行的整体。写进每个快照的考辨文字、虚线残影的盈亏表达、诗词路线的任意门，都说明作者真正追求的是帮助使用者建立时空直觉。

对历史爱好者、语文和历史教师、内容创作者，它是一个难得的直观教具；对前端开发者，这个零依赖的自研 GIS 也是研究几何压缩和状态驱动渲染的优秀样本。但合理的预期是：它是一扇带你走进历史的门，而不是替代原始史料的最终结论。
