# 逐行读完一个浏览器 AI 试衣间的源码：隐私优先的静态站长什么样

当一个工具要求你填写 API Key、上传真人照片时，一个理应被追问的问题是：这些东西去了哪里？市面上不少 AI 试穿产品把账号注册和服务器中转作为默认形态，用户很难验证自己的数据究竟如何被处理。最近我注意到一个思路相反的开源项目 [PoseWear 衣姿](https://github.com/atuizz/posewear)，它只有 108 个 Star，2026 年 10 月底才建仓，却把"数据不离开浏览器"做成了可逐行审计的实现。这篇文章基于它的源码，谈谈一个隐私优先的纯静态站点在工程上是怎么成立的，以及它没有明说的版权边界。

## 一、产品形态：参考图库与试穿工作台的结合

先厘清它是什么。PoseWear 不是大模型，也不是传统意义上的 SaaS，而是一个部署在 Cloudflare Pages 上的纯静态站点，由两部分构成。

![一次 AI 试穿的完整流程](media/flow.png)

其一是三套参考图库：多角度姿势线稿、1439 个条目且附日文原名的深度姿势、按季节和类型分类的服装，以及 CC0 协议的人像脸模。每个素材都有中文描述和可复制的中英文提示词。其二是试穿工作台：上传自己的人物照，选择服装与姿势，配合模型 API 生成试穿图，也支持不传照片、纯靠文字与参考出图，具备多张生成、前后对比、单张与打包下载能力。

服务商层面支持 OpenAI、Gemini、豆包 Seedream 以及任意 OpenAI 兼容的自定义中转。需要强调的是，PoseWear 本身不提供模型算力，所有生成费用都从用户自己的服务商账户扣除。

## 二、无框架的原生技术栈，换来的是可审计性

这个项目的技术选型相当克制。前端没有使用 React、Vue 之类的框架，就是原生 HTML、CSS 与 JavaScript：负责图库、搜索、收藏、灯箱和 hash 路由的 app.js，负责服务商适配与生成逻辑的 studio.js，核心代码加起来只有一千多行。离线能力由 Service Worker 提供，整体可以作为 PWA 安装。

构建侧使用 Python，负责生成 WebP 缩略图、独立详情页、sitemap 和安全响应头；测试用 Playwright 拦截服务商接口，模拟密钥错误、限流、5xx、超时和安全拦截等情形，整个测试过程不需要真实密钥。轻依赖带来的直接收益是可审计性——想确认它如何处理你的密钥和照片，阅读那几个源文件即可，不必在庞大的框架抽象里追踪数据流。

## 三、隐私设计：四条可以在代码里核对的防线

对一个处理密钥和真人照片的工具，隐私不能停留在声明。我核对了它的具体实现，确实有四层相互独立的机制。

![密钥、代理、CSP 与本地存储四层安全设计](media/security.png)

第一层是密钥不上服务器。API Key 只保存在浏览器 localStorage，默认情况下浏览器直接调用服务商官方接口，PoseWear 的站点完全不经手，设置页提供一键清除。

第二层是可选代理的四道闸。只有用户手动开启代理，或使用因浏览器跨域限制而必须中转的豆包时，请求才会经过它的 Pages Function。阅读代理源码可以看到：它校验 Origin 和 Referer 必须同源；只允许转发到官方接口域名白名单，自定义中转需要显式声明且路径符合图片接口规范；拒绝 localhost、内网段和非标准 https 地址；并按 IP 在 60 秒窗口内限流。代码注释明确写着只转发、不记录、不存储请求内容与密钥，响应也带 no-store 头。

第三层是严格的内容安全策略。构建期生成的 CSP 把 connect-src 限定在几家厂商域名，object-src 设为 none 禁止插件，frame-ancestors 设为 none 防止被第三方 iframe 嵌套造成点击劫持，脚本采用哈希白名单。这意味着即便页面出现注入点，恶意脚本也难以把数据外传。

第四层是数据本地持久化。收藏、最近使用和生成历史都存放在 IndexedDB，支持导入导出与删除撤销；项目没有账号体系，也没有后端数据库，从架构上消除了服务端泄露用户素材的可能。当然，这些机制并不免除在公共电脑上使用后手动清除密钥的必要。

## 四、降低审核误杀：一套有分寸的双语词表

真人照片搭配泳装、内衣等服装时，很容易触发服务商的内容安全审核。PoseWear 默认开启的"减少误拦截"功能，其实现方式值得专门分析。

![敏感词如何中性化成电商目录措辞](media/neutral.png)

在 studio.js 中有一个 NEUTRAL 正则数组，包含中英文两套替换规则，它只改写发送给服务商的提示词措辞，完全不改动用户选择的服装、姿势和参考图。例如把"性感、火辣"替换为"时尚"，"低胸"替换为"V 领"、"露背"替换为"开背设计"，"比基尼"替换为"泳池边时装"，"内衣"替换为"内搭"，而"裸露"类词汇直接删除，最后统一附加一段强调成年人、完整穿着、款式剪裁一致的专业电商试穿框架描述。

这套设计的分寸感在于目标清晰：它降低的是正常穿搭被机审误判的概率，而不是帮助规避对真正违规内容的审核。文档也明确说明违规内容该拦截仍会被拦截，建议此时更换服务商或服装；并且该功能可以一键关闭，按原始提示词发送，把选择权留给用户。

## 五、理性看待边界：素材版权是最需要警惕的部分

![适用场景与能力、版权边界](media/limits.png)

使用门槛方面，仓库本身不包含任何图片素材，自行部署需要先运行下载脚本从原作者图库拉取数 GB 数据，再执行构建；生成成本由所选服务商决定，通常每张约半分钟；审核严格程度上 OpenAI 最高，Gemini 与 Seedream 相对宽松。

更重要的是版权边界，这里必须把许可证的覆盖范围讲清楚。项目的 MIT 许可只覆盖代码、页面文案和构建脚本，并不覆盖任何图片与数据：姿势线稿和服装图的版权归原作者所有，原站并未标注开放许可，转载、商用或二次分发需要先取得授权；深度姿势图采用页面热链方式、根本不进入仓库，仓库内只有文本元数据和中文译名；人像是 AI 生成的虚构人物、采用 CC0 协议，理论上可商用且无需署名，但原作者希望不要原样批量转载，也明确不能用来冒充真人。自行部署时还需要保留页面中的来源与作者说明。

此外它仍是一个非常年轻的项目，增量素材更新、生成记录导出等路线图功能尚未完成，生态成熟度有待时间验证。

## 结论

PoseWear 的价值不在于功能多么颠覆，而在于它示范了一种克制而坦诚的工程态度：用无框架原生代码换取可审计性，把密钥和数据限制在用户本地，把代理与 CSP 的每一条规则都摊开在源码里，连素材版权的灰色地带也在文档中明确划线，而不是用一个笼统的 MIT 标签让人误以为图片也可自由商用。

对于重视隐私、需要快速产出穿搭参考的电商运营、自媒体与设计师，它提供了一个自部署成本极低、数据流向清晰可信的选择。但合理的预期是：它是一个轻量参考工具而非全能设计平台，模型调用费用、素材授权合规这些责任最终仍在使用者自己手里。
