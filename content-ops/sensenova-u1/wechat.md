先说一个我克隆商汤 SenseNova-U1 仓库后才发现的反直觉事实：它名字里写着 8B-MoT，但实际总参数是 175 亿（17.552B），差了一倍还多。

这个误会不是文字游戏，而是理解整个项目的钥匙。今天就从我本地逐文件核验的结果出发，聊聊商汤这套 NEO-unify 原生统一多模态架构到底在做什么，以及普通人能不能在自己显卡上跑起来。

## 8B 为什么其实是 175 亿

很多人看到 8B 就以为是个 80 亿参数的小模型，这是第一个坑。仓库里专门有一份参数分解文档，还配了脚本让你加载权重后自己数。我核对了结果：总参数 17.552B，bf16 下大约占 35.1GB。

![8B-MoT 真实参数拆解](/images/sensenova-u1/02-parameter-breakdown.png)

它分成三块：生成 transformer 8.186B、理解 transformer 8.121B、共享层 1.245B（就是词嵌入和输出头）。按激活通路算，理解通路 9.366B、生成通路 9.431B，共享层在两边各计一次。

这里的 MoT 是 Mixture-of-Transformers，混合 Transformer，不是更常见的 MoE。理解和生成是两套独立专家，运行时按任务只激活一套，再共享文本输入输出层。所以名字里的 8B 说的是单条通路的量级，不是整个模型。做显存规划前一定要读参数分解，望文生义很容易翻车。

## 它反对的是"模块拼接"

要看懂这个项目，得先看懂它在跟谁对照。

![模块拼接与原生统一两条路线](/images/sensenova-u1/01-architecture-compare.png)

过去的多模态系统基本是拼接派：一个视觉编码器看图、一个大模型当大脑、再挂一个 VAE 加扩散模型画图，三个模块各有各的权重，靠胶水代码连起来。能用，但问题也明显：模块多、占显存、理解和生成没法端到端联合优化，想在一段话里图文混排还得来回搬运。

NEO-unify 走原生统一：理解专家和生成专家放进同一个模型，共享嵌入层和输出头。到 U1.5 更进一步，干脆把独立视觉编码器和 VAE 都去掉了，用无 VAE 的视觉路径加空间连续重建，靠 flow-matching 做生成，支持原生 4K。我在源码目录也确认了，理解和生成的建模文件确实在同一套 neo_unify 代码里，不是两个项目硬拼。

这里值得停下来解释下"去掉 VAE"意味着什么。传统扩散模型依赖一个变分自编码器（VAE）在像素和隐空间之间来回压缩、还原，它本身就是一块独立的参数和算力开销，压缩过程还会丢细节。NEO-unify 改用一套统一的视觉表征直接做空间重建，等于把"看懂图"和"画出图"对齐到同一个表示空间里，少一次翻译，理论上更利于图文交错和编辑时保持一致性。这也是它能把模块数压下来、进而谈单卡部署的底层原因之一。

## 最能体现统一优势的是"自修正"

这个能力在最新的 U1.6 上最典型。

普通模型想做"画完自己检查再改"，通常得在外面搭一个 agent 循环：让另一个模型看图、挑错、再调生成接口，跨模块来回传图。U1.6 因为同一个模型既看得懂自己刚画的图、又能重新画，所以能把生成、检查、修改塞进同一次生成里。它做完一张信息图，会自己对照提示词检查错字、乱码、编号错误，然后直接出修改稿。

官方给的数据是：综合美感比 U1.5 提升 10%，高文字密度信息图任务上，自修正比单次生成平均提升 7%。这两个是官方基准和主观评测数据，第三方复现还有待观察，我先把这个限定放在这里。

## 三代演进，各自解决什么

![U1 到 U1.6 的三代演进](/images/sensenova-u1/03-version-timeline.png)

U1 是首发，验证一个模型同时会看图和画图这条路能走通，提供 8B、A3B 和图文交错权重。U1.5 是架构关键一跃，去掉独立视觉编码器和 VAE，补上原生 4K、文字渲染和图像编辑。U1.6 就在今天（11 月 24 日）发布，重点从"能做"转向"好看且准确"，主打美学提升和原生自修正，还发了 4 步、8 步蒸馏模型并正式上线 ComfyUI。

让我意外的是它的工程完整度。我数了代码：推理和模型代码约 1.1 万行，训练代码高达 5.18 万行，还有 13 个测试文件。这不是只给几个推理脚本的发布包，而是把训练流程也开放了。示例覆盖文生图、图像编辑、图文交错、视觉问答、服务化五类任务，依赖却很克制，直接依赖只有 12 个，用 uv 锁环境、Python 3.11，文档还做了彻底的中英双语。

测试也不是摆设。我逐个对了文件名，CFG 批处理、生成式 RoPE、分组矩阵乘这些关键算子都有对应测试，层卸载、量化产物、GGUF 加载、LoRA 也都有专门校验。运行时工具目录里 layer_offload、quant_runtime、gguf_loader、profiler 一应俱全——这正好解释了单卡 24GB 怎么吃下 35GB 的全量权重：靠分层卸载加运行时量化，而不是让用户硬扛显存。另外仓库根目录还有个 AGENTS.md，专门给 AI 编程助手规定读文档的入口，对用 Claude Code、Codex 这类工具的人很友好。

## 你的显卡能不能跑

这是最实际的问题。先给结论：能本地跑，但不是消费级小卡能轻松驾驭的。

![本地部署的权重选型与适用人群](/images/sensenova-u1/04-deploy-matrix.png)

官方参考配置是单卡 24GB 显存加 64GB 系统内存，再给权重预留约 35GB 磁盘。最小路径很直接：克隆仓库、uv 同步环境、hf download 下权重、跑 t2i 推理脚本。

权重按硬件分四种：要完整效果用 BF16 原版，但得 35GB 显存；24GB 单卡选 FP8 或 INT8 的 Native 量化；显存更紧、习惯 llama.cpp 生态的用 GGUF 的 Q4_0、Q6_K、Q8_0；想出图快就配 4 步或 8 步 LoRA，注意 LoRA 是适配器，必须搭基座。它能压进 24GB，靠的是层卸载、运行时量化这些工具一起发力，不是让你硬扛。

具体跑通其实就四步，我把官方最小路径核对了一遍：先 git clone 仓库，用 uv sync 按锁文件建 Python 3.11 环境（依赖走 cu128 的 PyTorch 源）；再用 hf download 把 U1.6-8B-MoT 权重下到本地 models 目录；然后执行 examples/t2i/inference.py，通过 bucket、aspect_ratio、num_steps、vram_mode、attn_backend 这几个参数控制分辨率、步数、显存模式和注意力后端；最后指定 output 出图。推理脚本还支持 jsonl 批量任务、lora_path、gguf_checkpoint、seed 和 think 开关，做批量评测或换量化方案都不用改代码。需要服务化的话，文档给了基于 Docker 镜像的 LightLLM + LightX2V 部署路径，把 X2I 生成服务单独分配 GPU，适合团队搭内部接口。

## 谁现在该上手，谁先等等

适合的人：研究统一多模态架构的工程师，这里有五万多行训练代码可学；要在单卡上同时做理解、生成、编辑、图文混排的开发者；做信息图海报、想用自修正减少返工的团队；以及已经在用 ComfyUI 的人，官方节点上线了。

先等等的人：只有 8 到 16GB 显存又不想折腾量化的，即使 Q4 也偏紧；只想调 API 不本地部署的，直接用官方在线 Demo 就行；纯做文生图、追求出图量、不需要理解能力的，成熟的 SD、Flux 生态可能更顺手。

最后提醒：代码是 Apache-2.0，但模型权重许可要看各个 HuggingFace 模型卡，两者不是一回事，商用前单独确认。

还有个容易被忽略的点：这个仓库同时挂了 HuggingFace 和 ModelScope 两个模型源，国内网络环境下从 ModelScope 下权重通常更顺畅，不必死磕海外源。它还提供在线 Demo（unify.light-ai.top）和 Discord、飞书社区，拿不准效果的话，建议先在网页端试几轮文生图和图像编辑，确认风格和文字渲染能力符合预期，再决定要不要花 35GB 磁盘和一张 24GB 显卡去本地化。对于团队而言，先评估自己的真实任务里"理解+生成一体化"到底占多大比重——如果只是批量出纯文生图，这套架构的优势发挥不出来，反而增加运维成本；但如果业务里大量涉及图文交错、信息图自修正、基于图像理解的编辑，它的统一架构就会省掉很多跨模块编排的麻烦。
