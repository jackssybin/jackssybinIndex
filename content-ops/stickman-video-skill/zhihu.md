# 装完这个 6972 Star 的火柴人视频 Skill，我理清了双引擎和 14 种画风的真实边界

无脸视频（faceless video）的真正门槛不在创意，而在重复的制作劳动：脚本、配音、配图、动画、字幕、音效，一条几分钟的视频往往要耗掉一个晚上。最近一个名为 [stickman-video-director](https://github.com/kaomei/stickman-video-director) 的开源 Skill 试图把这套流程交给 AI Agent 自动完成，让话题、文章或脚本直接变成带旁白、字幕和音效的火柴人视频。

与只阅读文档不同，我先在本机完成了真实安装并跑通官方自检与项目初始化。这篇文章基于一手过程，谈四个问题：它的实际构成、双引擎设计、14 种画风如何选择，以及它的能力边界。

## 一、556MB 的 Skill：不是提示词，而是方法论加渲染器

很多人对 Skill 的印象是一段提示词，但这个项目的体量和结构都更接近一个完整的生产系统。安装到本地技能目录后实测体积为 556MB，构成相当能说明问题。

![双引擎心智模型与共同底座](media/engines.png)

它包含 73 份 references 契约文档，把每种画风的视觉语言、字幕字体与位置、镜头节奏、音效处理和验收标准写成 Agent 必须遵守的规范；57 个可执行脚本，以 autopilot.mjs 为统一入口，下挂渲染、字幕对齐和各风格专用运行时；47 个测试文件、共 485 项断言，这在同类 Skill 中并不多见，目的是约束 Agent 不能偷工减料；还有一个 253MB 的本地音效库，使 B 模式的环境音和动作音效可以完全离线获取。

运行时依赖反而克制：Node 20 以上、FFmpeg/FFprobe、@napi-rs/canvas 与 sharp 两个图像库，外加 5 个 OFL 开源字体。我在 Node v22.22 上安装依赖后运行官方 doctor，node、ffmpeg、ffprobe、canvas、sharp、字体和 B4 钩子字体七项检查全部通过。

## 二、双引擎：两条只共享安装的独立路线

理解这个 Skill 的关键，是区分两条产物、成本和契约都不同的制作路线。

A 模型引擎本质是导演与提示词工程。Agent 负责确认故事、风格、画幅、时长和声音方案，输出分镜和独立可用的视频生成提示词，然后可选地通过内置浏览器操作 Google Flow 等 AI 视频服务，先以最低分辨率试片、用户确认后再连续制作。它的默认交付停在提示词，是否消耗外部额度由用户授权决定。

B 代码引擎才是真正的本地自动成片。它用 canvas 绘制插画和微动画、本地 TTS 生成旁白、按语音对齐字幕、混入本地音效，最后由 FFmpeg 在本机渲染 MP4，全程不上传素材。我实测初始化一个 B1 项目时，命令会在技能目录之外生成 project.json 脚手架，并明确提示需要先补充旁白、字幕和场景才能渲染，而不是假装一键完成。

作者在文档中反复强调一条我认为很专业的约束：A 与 B 只共享安装，不共享生产契约。A 的片段时长规则和声音画像不能搬到 B，B 的本地渲染约束也不适用 A；当缺少工具时，明确禁止偷偷回退到 Gemini、ElevenLabs 或系统 TTS，做不到就如实降级并说明，绝不伪造通过。

## 三、14 种画风：选的是生产规范，不是皮肤

技能内置 A、B 各 7 种、合计 14 种画风，差异远不止配色。

![14 种画风全景与 A/B 分组](media/styles.png)

A 模式包括 A1 经典黑白、A2 现代潮酷、A3 史前洞穴、A4 治愈故事、A5 历史卡通、A6 暖金暗影和 A7 橡皮管动画；B 模式包括 B1 极简线稿、B2 彩色手绘、B3 复古电视、B4 求生短剧、B5 角色解说、B6 动感 Meme 和 B7 像素剧场。

契约文档里有大量硬性规则。B1 到 B4 字幕最多一行，B5 允许最多三行语义字幕；B4 求生短剧要求每个镜头和静止画面状态不超过 3 秒，并设有前三秒视觉升级门禁和恐怖可见度门禁；B6 动感 Meme 竖屏 9:16 效果最好，配有 35 项验收矩阵和角色绑定契约；B7 像素剧场走纯代码像素画，不依赖任何图像生成服务。技术实现上，B1 到 B4 共用一个清单渲染器但规则彼此独立，B5、B6、B7 各有专用运行时，全部原生支持 16:9 和 9:16。因此选择风格本质上是选定一整套画面、字幕、节奏、声音和验收规范。

## 四、B 模式本地出片的六步链路

顺着 autopilot.mjs 与 autopilot-core.mjs 的源码，可以把代码引擎的链路整理为六步，我实际验证了前两步。

![B 代码引擎本地出片六步流程](media/workflow.png)

第一步 doctor 自检环境，缺什么会明确告知而不是中途报错；第二步 init 在技能目录之外建立工程，project.json 保存阶段、指纹、审批状态和断点以支持中断续做；第三步 Agent 写剧本并由 TTS 生成连续语音轨，文档要求先有声音再定画面；第四步通过 align_captions.py 按真实停顿和语义对齐字幕，明确反对按固定字数机械切分；第五步本地渲染，canvas 绘制关键帧与微动画，且微动画必须推动语义，单纯全局缩放淡入淡出不被认可，再由 FFmpeg 合成；第六步验收交付，输出 MP4、SRT/VTT 字幕、联系表和校验报告，并要求 Agent 以正常速度带声音实际审看成片，技术检查通过不等于创作验收通过。

工程上还有几个值得注意的设计。渲染器只读声明式 JSON，绝不执行素材中夹带的代码、shell 片段或 URL，从机制上防范提示注入；镜头缓存采用内容寻址，中断后可以续渲；通常画面静止不超过 2.5 秒以维持信息密度。为验证 B6，我还为系统 Python 3.11 补装了 numpy、Pillow 和 opencv，使 B6 的三项专项检查也全部通过。

## 五、能力边界与适合人群

![能力边界与适用人群](media/limits.png)

它真正擅长的是无脸 YouTube 与短视频频道的批量制作，以及知识解说、故事、Meme、像素短剧这类旁白驱动、图形化表达的内容；对追求可复现、不依赖云端、希望本地化交付的团队，以及本来就使用 Claude Code 或 Codex 的创作者契合度较高。

但边界同样清晰。其一，它不是一键傻瓜软件，整个流程依赖 Agent 驱动，需要使用者理解审批门禁，纯新手存在学习曲线。其二，A 模式依赖外部视频服务与额度，API key 通过环境变量传入，技能本身不附赠订阅。其三，TTS 与生图需要自行配置，它不绑定特定供应商，缺少适配器时应实现项目级适配而非期待万能兼容。其四，556MB 的体量真实存在，其中音效库占 253MB，部分风格还需要额外的 Python 科学计算栈。其五，风格契约严苛，每个 B 风格有独立验收矩阵，不允许跨风格偷懒或随意降级，这保证了下限，也意味着无法指望随便操作就产出爆款。

## 结论

这个项目最有价值的地方，在于它没有把 AI 自动生成当作降低标准的理由，而是用 73 份契约、485 项测试和一道道实际成片评审门禁，把成熟导演的工作方法固化为 Agent 可执行的流程，并坚持做不到就如实说明、不伪造结果。

如果你已经在用 Claude Code 或 Codex，又想做无脸解说或知识动画，它值得纳入工具箱，建议从 B1 极简线稿这种本地零成本路线起步；但需要清楚它的定位是能力很强的导演副驾，选题、脚本和最终验收始终掌握在使用者自己手里。
