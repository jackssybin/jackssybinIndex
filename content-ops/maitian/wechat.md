先说一个让我有点意外的数字：麦田（mdldm-maitian）这个 GitHub 项目，创建于 2026 年 11 月 14 日，我克隆它的 11 月 27 日，才过去 **13 天**，就已经有 **2303 个 Star、598 个 Fork**。

一个两周的个人项目凭什么涨这么快？我把仓库完整拉下来逐文件看了一遍，还把它的测试真跑了一遍。结论是：它切中的痛点足够普遍，而它对「自动化边界」的克制，才是真正值得讲的地方。

## 每个多平台博主都懂的痛

如果你同时做 B站、抖音、小红书、视频号、YouTube、X、Instagram，一定懂那种感觉：一条视频剪好了，真正的体力活才刚开始。

![一期视频要在七个平台手动发七遍](/images/maitian/01-pain-vs-maitian.png)

每个平台标题字数限制不同、正文风格不同、封面比例不同、话题规则也不同。你要打开七个创作者后台，重复七遍「上传、传封面、贴文案、设定时、点发布」。更焦虑的是发完之后：哪期在哪个平台起来了？哪个平台在涨粉？哪个平台真带来了付费？数据散在七个后台，没有统一入口。

麦田的定位一句话讲清：**Agent 驱动的自媒体发布工作台——你对 AI 说一句「整理发布」，一期视频填好七个平台，数据每天自己回来。** 它的作者麦当是做 0 基础 AI Agent 教程的博主，这套系统是照着自己每天发视频的流程，一边发一边改出来的，不是凭空设计。

## 三层架构，各管一段

我本以为这类工具就是一个大脚本模拟点击，打开源码发现它把职责拆成了清晰的三层，这是它没变成屎山的关键。

![麦田的三层 Agent 架构](/images/maitian/02-three-layer-architecture.png)

**第一层是发布 Skill**，装进 Claude Code 或 Codex。它负责看片、纠错、给每个平台写差异化文案，再生成标准化的 publish.json 并校验。我读了它的 SKILL.md，每个平台的文案章节、字段名都规定得很死，因为后续脚本就靠这些字段名取文案。

**第二层是麦田发布助手，一个 Chrome 扩展**，在应用商店上架、自动更新，负责真正打开上传页、传视频封面、填文案、设定时。把易变的平台适配逻辑放在可热更新的扩展里很聪明——平台改版时扩展更新一次，所有人自动生效，不用动主程序。

**第三层是麦田 Hub，一个 Node 守护进程**，也是仓库主体，管分发计划、调度、防重、等你点发布、取链接、采数据，外加网页大屏和飞书通知。它用 Node 22.5 内置的 node:sqlite，数据存本地 data/hub.db，不用额外装数据库。

我数了代码量：src 目录 35 个文件 3529 行，全仓库 JS/MJS 共 70 个文件 6064 行。对这么多功能的系统来说，体量相当克制。

## 最反直觉：它故意不帮你点发布

这是我最想讲的一点。

市面上的「自动群发」「群控」工具，卖点都是「全自动、无人值守、一键全发」。麦田反着来：**国内的 B站、抖音、小红书、视频号四家，它只把表单填好就停，最后那一下「发布」必须你自己点**，守护进程每 20 分钟提醒一次。

![自动提交与人工点发布的边界](/images/maitian/03-auto-vs-manual-boundary.png)

我在配置文件里核对了这个划分：人工点发布的是 bilibili、douyin、xhs、channels 四家国内平台；回读核对后自动提交的是知识站、X、YouTube、Instagram、Threads 五家。

为什么？因为作者清楚平台风控逻辑。全自动批量发布恰恰最容易触发风控、导致封号。把「填写」这种重复劳动自动化，把「发布」这个不可逆的高风险动作留给人，是一条能长期用下去的安全边界。README 的「各平台的坑」一节几乎全是这种实战经验：

- 小红书只走最保守的路：只读已渲染内容、像人一样滚动点击，不直接调接口，保持低频；
- 同一条视频每平台只传一次，反复重传最容易触发风控，中控专门做防重；
- 视频号定时可能被平台自己改掉（作者真遇到过 +2 小时），sync 会比对平台记录和计划，不一致就发飞书告警。

这些不是正确的废话，是真踩过坑才写得出的细节。

## 不只是发布，而是复盘闭环

只能发的话，它和普通工具拉不开差距。麦田另一半价值在数据，用农业隐喻分成三段。

![播种、长势、收成的数据闭环](/images/maitian/04-data-loop.png)

**播种就是发布**，按批次填好七平台、排进计划。批次也有讲究，建议国内平台两两一批，因为一次传太多会抢带宽导致超时。

**长势是流量和粉丝**，每天上午自动采一次各平台播放、互动、粉丝；新内容头三天每 6 小时采一次，抓住冷启动窗口；采集失败保留上次成功数据，不会让大屏空白。

**收成是转化**，接上自有站点后，靠 UTM 参数追踪是哪期、哪个平台带来了注册、会员、订单和收入，形成「播放→注册→会员→收入」漏斗。

更打动我的是复盘机制：每期发布后第 1、3、7 天自动出复盘卡片，做同龄对比（第 N 天对第 N 天，不拿老内容的成熟期欺负新内容），每周一自动出周报。这套节奏和专业运营的手动复盘习惯完全一致，只是它自动做了。

## 安全边界，最该学的部分

这类能登录你所有账号的工具，信任是第一位的。

![麦田的安全与风控设计](/images/maitian/05-safety-risk-control.png)

最关键一条：**它不存任何平台密码**。它操作一个专用 Chrome，用你自己登录好的登录态（通过 CDP 9333 端口通信）。我核对了 .gitignore，config.json、data/、chrome-profile/、logs/ 这些敏感路径全部不进 git。

加上前面说的不调接口、不重复传、人点发布，它还只读你自己账号的创作者后台，**不做任何互动自动化、不碰别人账号**，从根上避开了灰产地带。不用的平台可停用，停用后不体检、不发布、不采粉丝。它甚至会校验视频必须是 faststart 编码（moov 在文件头），否则小红书报「无视频流」、抖音出不了表单，这一步在 validate 阶段就拦下。

## 三级上手，不必一次配齐

![L1/L2/L3 三档上手路径](/images/maitian/06-three-levels.png)

**L1 只看数据，约 30 分钟**：装上麦田、在专用 Chrome 登录各平台，就能拿到全平台粉丝、播放互动、网页大屏和飞书日报，已发内容用 hub adopt 登记。

**L2 分发，再加 1 小时**：装 Chrome 发布助手和发布 Skill，就能一期填好七平台、定时发布、自动取链接。

**L3 转化，看站点开发量**：按 src/site.mjs 接口接上自有站点，才能看到注册和收入归因。

安装给了三种：macOS 一行脚本、Windows 的 PowerShell（社区贡献）、以及最有意思的「Agent 自动安装」——你把一段话复制给 Claude Code，它自己读指引、装好本体还把 Skill 装进自己的技能目录。环境要求是 macOS 或 Windows 10/11、Node.js ≥ 22.5、Chrome。

## 我实跑了测试：149 个全过

光看 README 不够，我把测试真跑了一遍。仓库有 26 个测试文件，覆盖 B站/抖音/小红书采集、飞书通知、小鹅通销售、站点转化、配置管理。跑下来 **149 个测试全部通过，耗时 9.2 秒，零失败**。对一个 13 天的个人项目，这个测试密度相当难得，说明作者在用工程化方式维护，也解释了为什么 7 个贡献者敢在这么短时间内协作。

## 谁适合，谁先等等

**适合**：同时运营 3 个以上平台、被重复发布折磨的个人博主和小团队；想要统一数据大屏、又不放心把密码交给云端 SaaS 的人；已经在用 Claude Code/Codex、想把发布也纳入 Agent 工作流的人；以及想学「Chrome 扩展 + Node 守护进程 + 本地 SQLite」桌面自动化架构的开发者。

**先等等**：只有单平台、发得不频繁的人，这套系统对你过重；没有一台常开电脑的人（它需要常驻）；追求完全无人值守、连发布都不想点的人——它在国内平台刻意不满足这个需求，而这恰恰是它的安全底线。

边界提示：麦田是 MIT 许可、可自托管，但它通过浏览器操作真实平台账号，任何自动化都存在平台规则变化的风险，重要账号建议先用小号验证节奏。它能降低重复劳动，不能让你无视平台规则。

项目 GitHub 地址：https://github.com/CzzzzzzJ/mdldm-maitian

在我看来，麦田最有价值的不是能自动发多少平台，而是它清醒地知道**哪些事不该自动化**。在一个人人鼓吹「全自动」的时代，这种克制反而成了最稀缺的产品判断力。
