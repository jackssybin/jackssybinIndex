先说一个我用 AI 干活时最烦的事：每次重开会话，都得重新交代背景，写代码的、写文案的任务还总在一个窗口里互相污染上下文。AI 单次能力已经很强了，缺的是"身份"和"编制"。

最近有个 8885 Star 的开源项目专门解决这个问题，叫 DS-Bot。我把整个仓库（核心 27 万行代码）克隆下来拆了一遍，今天聊聊它怎么把 DeepSeek Harness 变成一支长期在线的 bot 团队。

## 每个 AI 都有工号、记忆和权限

普通多 agent 框架给你的是编排原语，agent 大多是短命的，跑完就散。DS-Bot 的核心概念是长生命周期 bot：每个 bot 是持久身份，有自己的记忆、工作文件夹、权限档位和固定模型，关掉窗口再打开，它还记得你的偏好和之前干到哪了。

![长生命周期 bot 团队的组织架构](/images/ds-bot/01-team-org.png)

团队里有个 Main Bot，默认叫 Chief，权限最高，能创建、修改、停用其他 bot，管群聊和文件夹。关键是这个分权不是界面上藏个按钮，而是在 tools.js 里用 rt.isMain 这种代码级判断强制的，普通 bot 根本调不到管理接口。

上下文满了它会自动开新会话，旧的保持可读，不会硬截断。你还能建隐私 bot：它的文件夹、记忆、聊天记录其他 bot 都读不到，对外发消息或写外部文件必须你手动批准，就算删掉它，保护还会持续到你手动解除。

## 群聊最大的坑其实是钱

多 bot 群聊有个很现实的问题：如果每条消息 5 个 bot 全部推理一遍，费用随人数线性涨，而且大部分回复没人看。

![群聊 token 经济学对比](/images/ds-bot/02-token-economics.png)

DS-Bot 的做法很像真实公司的管理幅度原则。每个群必须设管理员，你的消息默认只让管理员回复，它判断该谁干再去调度；你直接 @ 谁，谁才会被唤醒；bot 之间派活走异步任务，接活的自己做完把结果发回群里，其他成员安静待命、零推理。做复杂任务还能开 Goal 模式：管理员先跟你对齐验收标准，再拆成阶段分给成员，逐段验收。

等于保留了多角色协作的形态，常规对话的推理量却压回接近单人对话。群聊还有独立记忆和工作文件夹，群外的 bot 看不到，避免信息串味。

这个设计背后其实是对多 agent 产品常见烧钱陷阱的修正。很多框架的演示里，一群 AI 七嘴八舌看起来很聪明，实际跑生产才发现每条用户输入都会触发全员上下文，token 消耗是单聊的好几倍，而且大量发言是重复表态。DS-Bot 把"谁该说话"变成显式调度：默认只有管理员这一个推理入口，@ 是定向唤醒，bot 之间派活则是任务队列而不是群聊广播。再配合 Goal 模式的阶段验收，长任务的模型调用被限制在明确的里程碑上，而不是每轮对话都全量跑。对要自己付 API 费用的个人和小团队，这个差别决定了多 agent 架构到底能不能长期用得起。

## 一套内核，四种部署形态

我实测它不是单一插件，而是同一套 bot 内核做了四种交付。

![四种部署形态与能力地图](/images/ds-bot/03-deploy-capabilities.png)

最省事的是 Electron 桌面端，Windows、macOS、Linux 都有安装包，自带锁定版本的 dsh，打开配好模型就能用，还能只读导入你原来 dsh 里的 bot 团队。已经在用 dsh 的可以直接从插件市场装 ds-bot 插件；有 NAS 或服务器的用 Docker，compose 一起，访问 13080 端口；移动端是正经用 Expo 写的 App，配合中继服务器还能在浏览器里远程用，设备之间走端到端加密配对。

能力都挂在 bot 身上：独立浏览器和登录态，发帖下载要你批准，遇到验证码付款发卡片交给你；电脑操控分只看、后台、前台三档，顶栏常驻指示条随时接管；能直接改 Word、PPT、Excel 并渲染图片自检排版。IM 接入有 8 个平台——微信、飞书、钉钉、企业微信、QQ、Telegram、Discord、Slack，电脑不用公网 IP。

还有个很实用的：你电脑上的 Claude Code、Codex、Cursor、GitHub Copilot、Devin、OpenCode、Gemini 等 10 种编程 CLI，可以直接收编成 bot，用它们自己的登录和套餐，照样进群、接活、共享记忆。

不过文档也很坦诚地列了限制：本地 Agent 走的是 CLI 自己的工具和上下文，DS-Bot 的共享连接器不会传给它，切换运行方式会新开一段对话；只有完全拒绝接入 MCP 的 CLI 才拿不到建 bot、派活这些团队工具。还有个 Cursor 的坑——它会把最后切换的模型存成全局默认，你在某个 Cursor bot 里选了具体模型，终端里其他 Cursor 会话也会跟着变，不想改全局就保持"CLI 默认"。这类细节如果不是真在维护的项目，一般不会写进文档。

日常使用上还有几个顺手的设计：耗时终端命令会自动转后台，bot 正忙时你直接发新消息，它会把当前任务挪到后台继续跑，前台始终能接话；顶栏有个类似灵动岛的区域看进度、批权限、追问或停止；可以用 /side 开侧边对话临时问一句；bot 还能直接在回复里画图表、表格、表单，或者跑定时任务。

## 安全模型：防什么、不防什么都写明白了

一个能操作文件、浏览器、邮箱的 agent，安全文档含糊最可怕。DS-Bot 专门有一份 SECURITY_MODEL.md，把信任边界和风险全部摊开，这在同类项目里很少见。

![安全模型与适用判断](/images/ds-bot/04-security-verdict.png)

它认定的首要威胁是提示词注入：网页、文件、搜索结果、其他 bot 消息都是不可信输入。防线有六层：Main Bot 代码级分权；密钥文件权限 600，可选 scrypt 加 AES-256-GCM 静态加密；密钥发给模型、写日志、出站请求时自动脱敏；隐私 bot 隔离；连接器拒绝非 HTTPS；HTML 组件走沙箱 iframe，Electron 开上下文隔离。

更值得肯定的是它诚实写明不防什么。静态加密护不住运行中的进程，内存里必须有明文密钥；Docker 版默认全权限加免审批，容器本身就是沙箱边界；隐私 bot 只隔离团队内 bot，不是系统沙箱，你给了终端权限它照样能读写系统；微信 QQ 受平台限制只能限时回复。这些没藏在 issue 里，而是正式安全模型的一部分。

工程纪律上还有条硬规则：永远不修改上游 dsh，所有功能只走插件 API。所以 dsh 快速迭代时它不会被甩下，27 万行代码其实是薄层加厚——agent 循环、模型路由、沙箱这些重活全复用上游，自己只做团队、记忆、群聊、IM 和桌面壳，运行时依赖只有 11 个，测试却有 282 个。

它还把对外连接管得很细。MCP 访问默认关闭，开启后会给每个本地客户端（比如 Claude Desktop、Cursor 或你自己的脚本）生成一个只显示一次的令牌，客户端只能访问你勾选的 bot 和群，隐私 bot 永远不在范围内，审批、提问、设置和密钥这些敏感操作也不允许 MCP 客户端碰。连接器可以登录 GitHub、Gmail、QQ 邮箱、163 邮箱和远程 MCP 服务，凭据存在本地密钥里，bot 看不到明文，写邮件默认还要你确认才发。这种"能力开放但密钥收口"的设计，跟它整体的安全模型是一致的。

## 谁该用，谁先等等

适合的人：已经在用 dsh 或编程 CLI、想把一次性会话升级成持久团队的重度用户；需要多 agent 分工和阶段验收、又在意 token 成本的小团队；想把 agent 接到微信飞书却没有公网服务器的人；在意数据本地化的用户——所有数据都在你自己电脑的 ~/.ds-bot，卸载也不删。

要缓一缓的：它还是 v0.3 预览版，391 个未关闭 issue，项目才 7 周，不适合直接押注稳定生产；非技术用户会遇到未签名拦截、Cookie 加密限制、Linux Wayland 兼容这些坑；只有单一聊天需求的话，这套组织架构是过度设计；另外所有 bot 烧的都是你自己的 API 额度，群聊再省钱，任务重了账单照样涨。

最后提醒：它是独立社区项目，不是 DeepSeek 官方，模型也不绑定 DeepSeek，兼容 Anthropic 消息格式的端点都能接。
