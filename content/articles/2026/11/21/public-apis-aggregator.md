想做个小工具、搭个 Demo、或者给 Side Project 找点真实数据，第一步往往不是写代码，而是满世界找"哪个 API 能白嫖、要不要 Key、浏览器能不能直接调"。GitHub 上有个仓库专门解决这件事——[public-apis](https://github.com/public-apis/public-apis)，一个收集免费公共 API 的清单，Star 数已经冲到 **50 万**，是全站 Star 量最高的项目之一。

但高 Star 不等于你真的会用它。这次我没有停留在"收藏等于学会"，而是把仓库完整克隆到本机、写脚本把那份 379KB 的 README 逐条解析了一遍，还跑通了它自带的测试。这篇文章讲三件事：这个仓库到底怎么组织的、哪些接口真能零成本调、以及——也是你这次最关心的——**拿这两千多个 API 聚合起来，到底能做出什么应用、有哪些值得做的方向**。

## 一、先看家底：一份 README 撑起 50 万 Star

很多人以为这种"awesome 清单"就是随手堆链接，public-apis 恰恰相反，它的工程化程度不亚于一个正经软件项目。

![仓库真实构成与工程化门禁](/images/public-apis-aggregator/structure.png)

我本地克隆后实测的核心数据：标准 API 条目 **2465 个**，分布在 **51 个分类**里，另外还有一个今年新增的 **MCP Servers 专栏，收录 60 个 MCP 服务器**；累计约 **2406 位贡献者、7019 次提交**，MIT 协议，主语言 Python，2016 年 3 月建仓，到今天仍然保持每日更新，没有归档。

它最反直觉的一点是：**整个仓库的"数据库"就是一份 `README.md`**。没有 SQLite、没有 JSON 数据文件，所有 API 信息都以 Markdown 表格的形式维护，每一行严格遵循六列契约：

```text
| API（含文档链接） | 描述 | Auth | HTTPS | CORS | Link |
```

其中 `Auth` 只接受 `No`、`apiKey`、`OAuth` 等固定枚举，`CORS` 只接受 `Yes`、`No`、`Unknown` 三个值。这种"用 Markdown 当结构化数据"的做法之所以没失控，靠的是一套强制质量门禁：

- `scripts/validate/format.py`：校验分类内字母序、字段数量、CORS 枚举值是否合法；
- `scripts/validate/links.py`：在 PR 阶段自动检查链接是否失效；
- `scripts/tests/` 下 **31 个单元测试**，我在本地用 CI 同款方式（`PYTHONPATH=. python3 -m unittest`）跑了一遍，结果是 **Ran 31 tests … OK，全部通过**；
- 3 个 GitHub Actions 分别管 push、PR 校验和链接巡检；
- `CONTRIBUTING.md` 明确写着：拒收营销性质的 PR，收录的 API 必须能被社区免费、公开调用。

换句话说，50 万 Star 的背后不是一份链接列表，而是一套"人工策展 + 自动化校验"的长期治理机制。理解了这一点，你才会明白为什么它能维护十年还可信。

## 二、能不能白嫖、能不能纯前端调：看这三张分布

对想做聚合应用的人来说，接口总数其实是最没用的指标，真正决定架构的是两个字段：**要不要认证（Auth）、浏览器能不能跨域直连（CORS）**。我把 2465 个接口全部统计了一遍。

![认证与 CORS 分布，以及 656 个可纯前端直连的接口池](/images/public-apis-aggregator/auth-cors.png)

**认证维度**：1200 个接口完全免认证（约占 49%），1104 个需要申请 apiKey（约 45%），150 个走标准 OAuth（约 6%），剩下 11 个是 Mashape Key、User-Agent 之类的小众方式。也就是说，接近一半的接口连注册都不用，直接发请求就能拿数据。

**跨域维度**：1080 个接口明确支持 CORS（44%），1055 个标注为 Unknown（43%），330 个明确不支持（13%）。这个比例要特别注意——标 Unknown 的不是不能用，而是清单没验证过，需要你自己发一次请求确认；明确标 No 的，浏览器直连一定会被拦，必须走后端代理。

两个维度取交集，得到一个对独立开发者极其友好的数字：**有 656 个接口同时满足"免认证 + 支持 CORS"**。这意味着什么？意味着你不需要服务器、不需要申请任何 Key、不需要处理密钥泄露，纯靠一个静态网页里的 `fetch()` 就能直连出数据——做原型、做 Demo、做黑客马拉松作品，成本几乎为零。

为了让这个数字不只是统计，我从池子里按分类抽了几个真实接口验证它的可用性思路：天气类有 Open-Meteo（面向非商业用途的全球天气预报，免 Key）、NASA POWER（太阳能与气象数据）；测试数据类有 DummyJSON（自带商品、用户、帖子的假 REST API）、FakerAPI；娱乐类有 Cat Facts、Dog Facts 这类随机事实接口；金融类甚至有 Billionaire Tracker 这种实时富豪榜。它们共同的特征是：注册零成本、文档清晰、返回标准 JSON，非常适合当聚合应用的"第一块拼图"。

另外提一句 HTTPS：2465 个里有 2377 个支持 HTTPS，只有 88 个还是裸 HTTP，安全基线整体不错。顺带说明一个解析时的发现：仓库里有 24 个条目的 HTTPS 字段标注了 `stdio`（其中部分同时支持 HTTP），这是给 MCP/本地进程类接口用的新形态，说明它的数据结构也在跟着 Agent 生态演进，而不是一成不变的老表格。

## 三、重点：2465 个 API 能聚合出什么应用？8 个可落地方向

这是这次你特别要的部分。我没有拍脑袋列点子，而是基于上面真实的分类条目数，挑出数据最厚、最适合聚合的赛道，每个方向都标注了依赖哪些分类、要不要 Key、难度和变现路径。

![8 个聚合应用方向矩阵](/images/public-apis-aggregator/ideas.png)

**① 个人数据仪表盘（难度★，订阅制）**
聚合天气（46 个）、加密货币（114 个）、金融（118 个）等分类，做一个一屏总览的私人看板：今天天气、持仓行情、汇率、待办一目了然。大量接口免 Key，是最适合新手的第一个项目，做好了可以走订阅或买断。

**② 垂直行业情报台（难度★★，B 端 SaaS）**
用政务（142 个）、新闻（26 个）、开放数据（98 个）做政策、招标、监管动态监控。这类接口大多需要 apiKey，但 B 端客户愿意为"省掉人工盯盘"付费，客单价高，是清单里商业价值最实的方向之一。

**③ 开发者 API 集市（难度★★，流量/佣金）**
基于开发类（251 个，全清单最大分类）和测试数据（37 个），做一个可分类检索、在线试调、一键收藏的 API 导航站。本质是 public-apis 的产品化升级版，靠 SEO 流量和付费置顶/佣金变现。

**④ 旅行规划聚合器（难度★★，CPS 分销）**
交通（103 个）+ 地理编码（120 个）+ 天气（46 个）+ 汇率（35 个）组合，输入目的地就给出路线、当地天气、汇率换算、景点信息。地图类接口多数要 Key，但酒店机票预订的 CPS 分佣模式很成熟。

**⑤ 健身运动数据站（难度★，广告+会员）**
运动健身（76 个）+ 健康（54 个），做赛事比分、NBA 等联赛数据、球队排名查询。这个赛道免 Key 接口密集，内容更新频率高，适合靠广告和会员增值变现。

**⑥ 娱乐内容盲盒（难度★，涨粉引流）**
游戏（120 个）+ 动漫（21 个）+ 音乐（39 个），做随机图片、梗图、猫狗事实、冷知识这类"一键来一条"的轻应用。技术门槛最低，价值不在直接赚钱，而在快速涨粉、给主产品引流。

**⑦ 加密/金融看板（难度★★，交易导流）**
加密（114 个）+ 金融（118 个）+ 汇率（35 个），做实时币价、法币汇率、富豪榜这类时效性强的看板。行情接口大多免 Key、更新频繁，常见变现是给交易所导流或做付费高级功能。

**⑧ MCP/Agent 工具网关（难度★★★，基础设施）**
这是最前沿的方向：仓库新增的 60 个 MCP 服务器加上 251 个开发类 API，可以做一个面向 AI Agent 的统一网关，解决鉴权、用量统计、请求路由。技术难度最高，但卡位的是 Agent 时代的基础设施，想象空间最大。

需要强调的是：不同方向会复用同一批 API（比如天气、金融被多个方向共用），所以各方向的数字相加会超过 2465，这很正常——2465 是去重后的接口总数。

而无论你选哪个方向，图底部那条琥珀色提示都是共同前提：**先做好"健康度巡检 + 统一缓存 + 鉴权代理"这三层底座**，否则免费接口的限流和失效率会很快拖垮你的产品体验。

## 四、清醒使用：它是目录，不是免运维的数据中台

最后必须祛魅。50 万 Star 很容易让人产生"靠它就能躺着做产品"的错觉，但它的边界其实非常清楚。

![能力边界与生产环境建议](/images/public-apis-aggregator/verdict.png)

它**是**人工策展的免费 API 黄页，字段规范、可按 Auth/CORS 筛选、跟进了 MCP 生态、MIT 协议允许自由复用元数据；但它**不是**一个数据服务平台——不保证收录的接口长期可用（当前有 2811 个未关闭的 open issue，其中不少就是接口失效反馈），不提供托管、SLA、统一鉴权或缓存，每个接口的免费额度和限流规则都由各服务商自己说了算，而且 43% 的接口 CORS 状态是 Unknown，前端能不能直连必须自己实测。

所以真要上生产环境，至少做三件事：后端加代理层、密钥永远不进前端；定时跑健康检查并配置自动降级的备用源；核心业务别只依赖单一免费接口；同时严格遵守每个 API 的服务条款，不要滥用爬取。

## 五、给新手的最小起手式

如果你看完想动手，我建议按这个顺序，避免一上来就被 Key 和跨域劝退。第一步，直接在 README 里用 `Auth = No` 且 `CORS = Yes` 两个条件筛，从那 656 个接口里挑一个你感兴趣的分类，比如天气或随机事实；第二步，先在浏览器开发者工具的 Network 面板里手动发一次 `fetch`，确认真的能返回 JSON、没有跨域报错，再写进代码；第三步，把这次请求包一层 try/catch 和超时处理，因为免费接口偶尔会抽风；第四步，等你的功能跑通了，再考虑加缓存、加备用源、需要 Key 的接口统一走后端代理。这样从"能跑的 Demo"到"能用的产品"是平滑演进的，而不是一开始就背上整套后端架构。

## 结语

public-apis 最大的价值，是把"找数据"这件极其耗时的脏活，变成了一个可检索、可筛选、有质量门禁的起点。它本身不构成壁垒——**真正的壁垒是你在它之上做的聚合逻辑、缓存策略、产品体验和接口选型**。

如果你是想练手的独立开发者，建议从 656 个"免 Key + CORS"接口池里挑一个方向（比如个人仪表盘或娱乐盲盒），一个周末就能做出能跑的第一版；如果你想认真做产品，就把它当免费数据的黄页和起手式，把功夫下在那三层底座上。
